# Job Applications Management System (JAMS) - Development Context

This document provides guidelines and contextual information for the development of the JAMS project.

## Project Overview

**JAMS** is a fullstack application designed to help candidates manage their job application processes, interviews, feedback, and company contacts.

### Core Technologies

- **Framework:** [Nuxt 4](https://nuxt.com/) (Vue 3, Nitro)
- **Language:** TypeScript
- **ORM:** [Prisma](https://www.prisma.io/) with SQLite
- **Styling:** [Tailwind CSS](https://tailwindcss.com/) with [@nuxt/ui](https://ui.nuxt.com/)
- **Package Manager:** pnpm

## Architecture and Folder Structure

- `app/`: Contains frontend logic (components, pages, layouts).
  - `components/`: Reusable global components.
  - `features/`: Business logic organized by features (e.g., `database/`).
  - `pages/`: File-based routing structure.
- `server/api/`: API endpoints running on Nitro.
  - Currently following a CRUD pattern, but many are still placeholders.
- `prisma/`: Database configurations.
  - `schema.prisma`: Defines the data model (Candidates, Applications, Companies, Steps, Feedbacks).
- `composables/`: Shared reactive logic (e.g., `useDatabase`, `useResponsive`).
- `utils/`: Utility functions and shared instances (e.g., `prisma.ts`).

## Development Conventions

### Error Handling
- **Domain Errors:** Always check `server/domain/errors/` for the most specific `AppError` subclass before throwing an error.
- **Custom Errors:** If no suitable error exists in `server/domain/errors/`, create a new one following the `AppError` base class structure, ensuring the correct HTTP status code is assigned.
- **Genereic Errors:** Never throw generic `Error` objects; use `AppError` subclasses to ensure predictable API responses.

- **Documentation:** Major blocks and complex functions must be documented following the **Google Documentation Style**. For internal or simpler logic, documentation is optional and should be used based on the complexity to ensure maintainability. All comments and documentation must be written in **English**.
- **Refactoring:** When refactoring code, you must also review and update any existing documentation to ensure it remains accurate and reflects the new implementation.
- **Testing:** When modifying a file that has a corresponding test file, the test file must be reviewed and updated as needed. This is mandatory if changes to core functionality would cause existing tests to fail, ensuring that the test suite always reflects the current state of the application.

### Backend and Database

- **Architecture:** Follow a pragmatic adaptation of **Clean Architecture** for TypeScript. Organize logic into layers (e.g., Controllers, Services, Repositories) to ensure separation of concerns, testability, and maintainability without unnecessary over-engineering.
- **Naming Convention:** All backend files must follow the **dot notation** pattern to explicitly define their responsibility (e.g., `auth.service.ts`, `user.repository.ts`, `application.controller.ts`).
- **Prisma:** Always use `pnpm prisma:migrate` when changing `schema.prisma`.
- **API:** Prefer using types generated by the Prisma Client to ensure type safety.
- **SQLite:** The local database is located at `prisma/dev.db`. There is a direct import/export feature for the `.db` file via the interface.

### Frontend

- **Nuxt UI:** Use components from `@nuxt/ui` (prefix `u-` or `U`) to maintain visual consistency.
- **Responsive:** Use the `useResponsive` composable for conditional logic based on screen size.
- **Tailwind:** Use Tailwind utility classes for fine-grained layout adjustments, following the Tailwind v4 setup in `assets/css/main.css` (`@theme`, `@custom-variant`, and tokens).

### Code Style

- **Semicolons:** The project does not use semicolons (following modern trends in the Vue/Nuxt ecosystem).
- **Imports:** Use the `@/` or `~/` alias for paths starting from the project root.
- **Clean Code:** Write clear, self-explanatory, and maintainable code. Follow standard Clean Code principles.
- **Control Structures:** All control structures (`if`, `else`, `for`, `do`, `while`) must use curly braces, regardless of the number of statements, to ensure consistency and readability (Google JavaScript/TypeScript Style Guide). Single-line `if` statements without braces are allowed only if they contain a single short statement and do not have an `else` clause.

## Common Commands

- `pnpm dev`: Starts the development server.
- `pnpm prisma:migrate`: Applies database changes.
- `pnpm prisma:studio`: Opens the Prisma visual interface to explore data.
- `pnpm build`: Generates the production build.
